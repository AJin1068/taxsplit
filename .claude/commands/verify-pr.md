이 레포의 **검증 Action**으로 일한다. 개발 세션이 아니다. 개발 세션의 대화·계획은 모르고, 알려고 하지 않는다.

대상 PR: $ARGUMENTS
(GitHub Action에서는 프롬프트가 PR 번호와 `needs-verify` 여부를 알려 준다.)

## 읽는 것 (이것만)

- 레포: `main`과 PR 브랜치. `git diff origin/main...HEAD`로 바뀐 곳을 본다.
- PR 설명·diff·라벨: `gh pr view <번호> --json number,title,body,labels,headRefOid,files,closingIssuesReferences`, `gh pr diff <번호>`
- PR이 닫는 Issue의 본문·코멘트: `gh issue view <Issue 번호> --json title,body,labels,comments` (`--comments`만 쓰면 빈 결과가 나올 때가 있다)
- `CLAUDE.md`, `docs/` (Issue의 "참고 문서"에 적힌 절을 먼저)

읽지 않는 것: `.env`(어떤 경로든), 레포 밖 파일. `eval/`은 읽기만 한다. 홀드아웃 시나리오는 찾지 않는다.

## 하지 않는 것

코드 수정·커밋·push, merge, 승인(APPROVE), 라벨 붙이기·떼기(`ready` 포함), `eval/`의 채점 규칙·정답 수정. 정답이 틀려 보이면 고치지 않고 "사람 확인 필요"에 적는다.

## 할 일

1. PR 제목의 "PR N"(작업 목록 번호, 예: `PR 4`, `PR 1k`)과 닫는 Issue를 확인한다. 닫는 Issue가 없으면 그 사실을 판정 근거에 적는다.
2. Issue의 "범위"·"정해진 결정"·"하지 않을 것"·"일반화 규칙"·"완료 기준"과 Issue 코멘트를 읽는다.
3. 다시 돌린 결과를 근거로 쓴다(`agent/`의 `uv sync`, `uv run pytest`, `uv run ruff check .`, `uv run ruff format --check .`). GitHub Action에서는 앞 단계가 이미 돌려 `.verify-out/checks.txt`에 남겼으니 그 파일을 읽는다. IDE에서는 직접 돌린다. 통과 수와 실패한 테스트 이름을 적는다. 완료 기준에 다른 확인 명령이 있으면 IDE에서는 돌리고, Action에서는 허용된 읽기 명령으로 확인할 수 없으면 "사람 확인 필요"에 적는다.
4. 완료 기준을 한 줄씩 대조한다. 각 줄에 결과(충족 / 미충족 / 확인 못 함)와 근거(명령, 테스트 이름, 파일:줄)를 단다.
5. diff를 읽고 찾는다:
   - "정해진 결정"·"하지 않을 것"·"일반화 규칙"을 어긴 곳
   - `CLAUDE.md` "설계 원칙"·"벽"을 어긴 곳 (LLM이 금액을 계산, 출처 없는 세법 숫자, 처리 코드·프롬프트에 시나리오 ID·가구 이름·사례 번호, 처리 코드가 `eval/` 정답을 읽음)
   - 이 PR 코드의 버그·위험
6. **점수 재측정**: PR에 `needs-verify` 라벨이 있을 때만 한다. 평가 하네스(PR 11)가 레포에 없으면 "점수 재측정: 아직 장치 없음(PR 11 이후)"이라고만 적는다. 있으면 PR 설명에 적힌 점수를 같은 명령으로 다시 재고 차이를 적는다. 라벨이 없으면 이 줄을 아예 넣지 않는다.
7. **다음 PR에서 할 일**(이 PR 범위 밖인데 고쳐야 할 것)은 코멘트에 넣지 않고 `followups.json`에 적는다(아래 "남기는 법").
8. **검증 장치 변경**: PR이 `.github/workflows/verify.yml`, `.claude/commands/verify-pr.md`, `.github/scripts/post_verify.py` 중 하나라도 바꾸면 이 검증 자체가 바뀐 장치로 돌았을 수 있다. 첫 줄 맨 앞에 "검증 장치 변경, 사람 확인 필요"를 넣는다. 올리는 스크립트도 이 경고를 따로 확인해 붙인다.

## `[검증]` 코멘트 형식

한국어로 쓴다. 전문 용어는 쉬운 말로 풀어 쓴다. 첫 줄은 정확히 이 모양이다:

```
[검증] PR N / 판정: 통과 | 조건부 통과 | 미달 / 기준 커밋 <짧은 SHA>
```

판정은 셋 중 하나만 쓴다. 미달: 완료 기준 미충족이나 막아야 할 버그가 있음. 조건부 통과: merge 전에 작은 수정이나 사람 확인이 필요함.

이어서 아래 칸을 이 순서로 쓴다. 해당 없는 칸은 "없음"이라고 쓴다.

1. `### 완료 기준` 표: 기준 / 결과 / 근거(다시 돌린 명령, 테스트 이름)
2. `### 점수 재측정` (`needs-verify`일 때만)
3. `### 정해진 결정·하지 않을 것·일반화 규칙 위반`
4. `### 버그·위험`: 항목마다 "막음 / 막지 않음"과 "이 PR에서 고칠지"
5. `### 사람 확인 필요`: 검증이 확인하지 못한 것과 그 이유
6. `### merge 전에 볼 코드 2~4곳`: `파일:줄` — 무슨 문제를 푸는 코드인지 쉬운 말로 — 왜 볼 만한지(면접 썰 포인트와 이어지면 함께)

넣지 않는 것: 다음 PR에서 할 일(7번처럼 Issue로), PR 설명을 다시 적은 것, 취향 수준 제안.

## 남기는 법

결과는 파일 두 개로 쓰고, 올리는 일은 스크립트가 한다. 같은 PR에는 `[검증]` 코멘트가 늘 하나만 남는다(새 커밋이 오면 고쳐 쓴다).

- `.verify-out/comment.md`: 위 형식의 코멘트 본문
- `.verify-out/followups.json`: 다음 PR에서 할 일 목록. 없으면 `[]`.

```json
[{"pr": "5", "title": "Issue가 없을 때만 쓸 짧은 제목", "body": "무엇을 왜 고칠지, 근거 파일:줄"}]
```

`pr`는 할 일이 걸리는 작업 목록 번호(제목의 "PR N"의 N)다. 해당 번호의 열린 Issue가 있으면 거기 코멘트로 달리고, 없으면 `ready` 라벨 없이 새 Issue가 된다.

- **GitHub Action**: 파일만 쓰고 끝낸다. 다음 단계가 올린다.
- **IDE (`/verify-pr`)**: 파일을 쓴 뒤 `python3 .github/scripts/post_verify.py --pr <PR 번호>`로 올린다. 먼저 `--dry-run`으로 무엇을 올릴지 보여 주고, 사람이 괜찮다고 하면 올린다.
