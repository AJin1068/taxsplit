---
description: 열린 GitHub Issue에서 다음 작업(PR 번호)을 골라 계획을 남기고, 사람이 정할 것이 없으면 바로 구현한다
argument-hint: "[PR 번호] 또는 [PR 번호들] --plan (예: 4, 14a, 4 5 6 7 --plan. 생략하면 ready 라벨이 붙은 열린 Issue 중 PR 번호가 가장 작은 것)"
---

이 레포의 개발 세션으로 일한다. CLAUDE.md의 "작업 순서"를 그대로 따른다.

대상: $ARGUMENTS
(비어 있으면 `ready` 라벨이 붙은 열린 Issue 중 제목의 "PR N" 번호가 가장 작은 것을 고른다. Issue 번호(`#13`)가 아니라 제목의 PR 번호로 고른다. 번호가 같으면 1 < 1c < 1d < 1e < 2, 14a < 14b 순서다. `ready` Issue가 없으면 그렇게 말하고 멈춘다. 번호를 직접 줬는데 `ready`가 아니면, 비어 있는 칸(범위·하지 않을 것·완료 기준·정해진 결정·참고 문서)을 알려 주고 멈춘다. Issue를 채우는 건 기획(Claude 앱)이 한다.)

`--plan`이 있으면 아래 "묶음 계획 (`--plan`)"만 하고 멈춘다.

0. `git checkout main && git pull origin main`으로 최신 `main`을 받는다. 커밋 안 된 변경이 있으면 멈추고 알린다.
1. `gh issue list --state open --label ready`로 대상을 고른다. `gh issue view <번호> --json title,body,labels,comments`로 본문과 코멘트를 읽는다(`--comments`만 쓰면 빈 결과가 나올 때가 있다). Issue 본문의 "정해진 결정"과 코멘트를 같은 무게로 따른다. Issue에 `needs-verify` 라벨이 붙었는지 적어 둔다.
2. CLAUDE.md, 대상 Issue의 "참고 문서"(`docs/prd.md`, `docs/design.md`, `docs/eval-plan.md`, `docs/adr/`의 해당 절), 손댈 코드를 읽는다. 직전에 merge된 PR 설명(`gh pr list --state merged --limit 3`)의 "다음에 할 것"·"확인해 주세요"(예전 PR은 "확인 필요") 중 이 Issue에 걸리는 것을 확인한다. `eval/`은 읽기만 한다.
3. 계획을 만들어 `[계획] PR N` 코멘트로 Issue에 남기고(기록용, 이미 있으면 고쳐 쓴다. 아래 "묶음 계획" 3번), 대화에도 보여 준다. 계획에는 바꿀 파일(빠짐없이), 접근 방법, 대안 1개와 트레이드오프, 완료 기준을 어떻게 확인할지, 그리고 아래 두 칸을 담는다.
   - `## 정할 것`: CLAUDE.md "작업 순서" 2번의 (다) 정답 데이터·채점 기준, (라) 돈이 드는 외부 서비스·데이터 정책, (마) 되돌리기 어려운 것만 적는다. 항목마다 추천안과 이유를 붙인다. 없으면 정확히 `- 없음` 한 줄을 쓴다(goal 연속 실행의 시작 조건이 이 줄을 읽는다).
   - `## 개발이 정한 것`: 묻지 않고 추천안으로 정한 것. 함수·파일 이름, 파일 배치, 테스트 방법, 구현 방식, 구조, 범위 안의 선택이 여기 들어간다. 세법 해석, (가) 범위 경계, (나) Issue·설계 문서에 없는 새 단계·화면도 여기 들어가는데, 이것들은 추천안으로 구현하고 `docs/assumptions.md`에 한 줄을 남긴 뒤 그 번호를 적는다. 추천안이 애매하거나 (가)·(나)에 해당하면 "사람 확인: TODO"로 둔다(막지 않음).
   - Issue 본문·코멘트("정해진 결정" 포함)·문서·ADR에 답이 있으면 "정해진 대로: …(출처)"로 적고 묻지 않는다.
   - **"정할 것"이 `- 없음`이면 승인을 기다리지 않고 바로 4단계로 간다.** 있으면 그것만 한 번에 묻고 답을 기다린다. 사람이 답하면(대화나 `plan-ok` 라벨) 4단계로 간다. 애매하면 묻는 쪽으로 판단한다.
4. "정할 것"이 `- 없음`이거나 사람이 답했으면 `main`에서 `<종류>/pr<번호>-<짧은 설명>` 브랜치를 만들고 CLAUDE.md 4~7단계(구현 → `uv run pytest`·ruff → PR 템플릿 채우기 → `Closes #<Issue 번호>`)를 따른다. merge는 하지 않는다.
   - PR 설명 "기록"에 `[계획]`의 "개발이 정한 것"과 구현 중 새로 정한 것(가정 목록 번호 포함)을 적는다. "확인해 주세요"의 "누가 답하나: 사람"은 (다)·(라)·(마)일 때만 쓴다.
   - PR 제목은 닫는 Issue의 제목과 똑같이 쓴다(예: Issue `PR 4: 계산 엔진 ①` → PR `PR 4: 계산 엔진 ①`). `feat: …` 같은 커밋 메시지 모양은 커밋에만 쓴다. (`gh pr create --title "<Issue 제목 그대로>"`)
   - PR을 열 때 Issue에 `needs-verify` 라벨이 있으면 PR에도 붙인다(`gh pr create ... --label needs-verify`, 이미 열었으면 `gh pr edit <PR 번호> --add-label needs-verify`). 검증 Action이 이 라벨을 보고 점수를 다시 잰다.
   - PR을 열면 검증 Action이 `[검증]` 코멘트를 단다. 판정이 "미달"이나 "조건부 통과"면 고칠 것을 보고에 적는다.
5. 끝나면 결과를 **한국어로, 쉬운 말로** 보고한다: 무엇을 했는지, 완료 기준 결과, PR 링크, 사람이 답해야 할 질문((다)·(라)·(마)만), 개발이 정한 것과 새로 생긴 가정 목록 TODO. PR 설명과 이 보고의 "사람이 답해야 할 질문"은 CLAUDE.md "PR 설명 쓰는 법"대로 요약하지 않고 풀어 쓴다(무슨 상황인가 → 확인할 곳 → 답에 따라 달라지는 것 → 추천).
6. 다시 부르면 다음 Issue를 1~3단계로 계획하고, "정할 것"이 `- 없음`이면 이어서 구현한다. 앞 PR이 merge되기 전에도 그 브랜치 위에 다음 Issue를 쌓아 진행할 수 있다. merge는 여전히 사람만, 쌓인 순서대로 한다. 쌓을 때는 앞 브랜치에서 새 브랜치를 만들고 `gh pr create --base <앞 브랜치>`로 연다.

## 묶음 계획 (`--plan`)

여러 Issue의 `[계획]`을 한꺼번에 남긴다. 사람은 "정할 것"이 남은 Issue만 답하고 `plan-ok` 라벨을 붙인다. 개발 세션·검증 Action·스크립트는 `plan-ok`를 붙이지 않는다. 기획은 앞 PR merge를 기다리지 않고 여러 Issue를 미리 채울 수 있다. `ready`는 기획이 Issue를 다 채운 **같은 메시지에서** 사람에게 승인을 묻고(결정 카드), 사람이 승인하면 기획이 붙인다(사람이 GitHub에서 직접 붙여도 된다). 승인 없이 붙이지 않는다.

1. 0~2단계를 PR 번호마다 한다. `ready`가 아닌 Issue는 계획하지 않고 끝 보고에 비어 있는 칸을 적는다.
2. 앞 번호의 계획이 바꿀 것을 뒤 번호 계획의 출발점으로 본다(쌓아서 진행하므로).
3. Issue마다 3단계와 같은 내용("정할 것"·"개발이 정한 것" 칸 포함)의 계획을 `gh issue comment <Issue 번호> --body-file <파일>`로 남긴다. 첫 줄은 `[계획] PR N`이다. 이미 `[계획]` 코멘트가 있으면 새로 달지 않고 그 코멘트를 고쳐 쓴다(`gh api -X PATCH repos/{owner}/{repo}/issues/comments/<코멘트 id> -F body=@<파일>`).
4. 계획에 "줄 확인"을 한 줄 넣는다. Issue의 "선행 PR"·"손대는 폴더" 칸(CLAUDE.md "goal 연속 실행")이 있는지, 계획이 바꿀 파일이 손대는 폴더 안에 다 들어가는지 본다. 칸이 없으면 "정할 것"에 적는다(칸은 기획이 채운다). 바꿀 파일이 손대는 폴더 밖이면 goal 연속 실행의 기계 검문 ⑥에 떨어지므로 "정할 것"에 적는다.
5. 코드는 쓰지 않고 브랜치도 만들지 않는다. 끝나면 PR 번호별 `[계획]` 코멘트 링크와 "정할 것"을 한 번에 보고한다. 사람은 "정할 것"이 남은 Issue만 답하고 `plan-ok`를 붙인다. "정할 것: - 없음"인 Issue는 그대로 goal 연속 실행을 시작할 수 있다.
6. `plan-ok`가 붙었거나 "정할 것"이 `- 없음`인 Issue는 `[계획]` 코멘트대로 진행해도 되는 것으로 본다. 다음에 `/next-issue <PR 번호>`로 부르면 계획을 다시 묻지 않고 4단계(구현)부터 한다. `plan-ok` 뒤에 Issue 본문이나 코멘트가 바뀌었으면 "기획이 바뀐 경우"대로 바뀐 부분만 묻는다.

## 기획이 바뀐 경우 (처음부터 다시 하지 않는다)

대상 Issue를 이미 계획했거나 브랜치가 있으면, 0단계 뒤에 지난번 이후 바뀐 것을 확인한다.
- Issue 본문·코멘트 변경, `main`의 `CLAUDE.md`·`docs/`·`eval/` 변경(`git log`/`git diff`로 지난번 읽은 커밋 이후).
- 대상 Issue의 열린 PR이 있으면 `gh pr view <PR 번호> --comments`로 PR 코멘트를 읽는다. `[검증]`으로 시작하는 코멘트(검증 Action이 새 커밋마다 고쳐 쓰는 한 개), 기획(앱)이 남긴 `[기획 확인]`·리뷰 코멘트는 고칠 지시로 본다(아래 순서로 반영). Issue에 새로 달린 `[검증]` 코멘트(이전 PR의 검증이 넘긴 할 일)도 같이 본다.
- 브랜치가 있으면 `main`을 그 브랜치에 merge한다(rebase·force push 금지).

**열린 PR의 `[기획 확인]`·`[검증]` 코멘트는 묻지 않고 반영한다.** 아직 반영하지 않은 코멘트가 있으면 "반영할까요"를 묻지 않고 한 덩어리로 처리한다.

1. 최신 `main`을 브랜치에 merge한다(rebase·force push 금지). 쌓인 브랜치면 앞 브랜치도 merge한다.
2. 코멘트가 말한 것을 고친다. 세법 해석이 새로 갈리면 추천안으로 고치고 `docs/assumptions.md`에 남긴다.
3. `agent/`에서 `uv run pytest`, `uv run ruff check .`, `uv run ruff format --check .`를 돌린다.
4. PR 설명을 다시 쓴다. 반영한 "확인해 주세요" 항목 제목 앞에 ✅(코멘트 링크), 넘긴 것은 ➡️(넘긴 Issue 링크)를 붙인다. 완료 기준 표·테스트 수를 고치고, 판정 스크립트로 "PR 무게" 칸을 다시 잰다.
5. 커밋하고 push한다. 설명만 고쳐도 검증 Action이 무게와 라벨을 다시 맞춘다.

코멘트가 CLAUDE.md "작업 순서" 2번의 (다)·(라)·(마)에 걸리는 새 판단을 요구할 때만 멈추고 묻는다. 그 밖의 바뀐 것(Issue 본문, `main`의 문서 변경)은 아래 표로 보여 주고, 표의 "고칠 것" 중 (다)·(라)·(마)에 걸리는 것만 승인을 받는다. 나머지는 바로 고친다.

| 바뀐 것 | 이미 한 계획·구현에 주는 영향 | 고칠 것 / 그대로 둘 것 |
| --- | --- | --- |

- 이미 만든 코드와 테스트는 버리지 않는다. 바뀐 요구에 맞지 않는 부분만 고친다.
- 완료 기준이 바뀌었으면 측정을 다시 돌린다.
- 사람은 "계속해줘" 또는 `/next-issue <PR 번호>`만 말하면 된다.
